# CLAUDE.md

Guidance for Claude Code in this repository.

## What this is

**Daftar for Linux**: a native Rust app (GTK 4, libadwaita, WebKitGTK 6.0) for an Obsidian vault in a Git repository, meant to replace Obsidian on a Linux desktop, a tiling Wayland compositor first. It is the sister of `notes-mac` (Daftar for macOS, Swift) and `notes-droid` (Daftar for Android, Kotlin). The three apps share no code, but they share rules: how a wikilink resolves, what a task line is and how it is ticked, the task statuses (`task_status.rs`, from the Tasks plugin's settings in the vault) and the `[reason:: …]` field (`TaskReason` in `task_line.rs`): a reason goes with the status it was given with, the format of the week notes in `Calendar/`, the config file and the colors. When a rule changes in one, change it in the others. A rule more than one app keeps is written down in `docs/specs/` (see [Adding a feature](#adding-a-feature)).

The repository is **public**; the vault it reads is private. Every test fixture is synthetic.

## Commands: always `just`

```bash
just test     # cargo test + node --test for the renderer
just lint     # cargo fmt --check + clippy -D warnings, as CI runs them, with the lints of [workspace.lints]
just run      # build and start; `just run Notes/Inbox.md` opens that note
just cli …    # the command line on the configured vault: `just cli tasks --due today`
just app      # the release binary
just web      # rebuild the reader bundle only
just install  # ~/.local/bin/daftar, its desktop entry and icon
just bench    # the core on a made-up vault of 20,000 notes, timed (crates/daftar-core/tests/bench.rs)
```

## Layout

```text
crates/daftar-core/   no GTK: parser, link resolver, tasks, index, search, config
crates/daftar-cli/    `daftar-cli`: the core on the command line, and notes-cli's picture cleanup
crates/daftar/        the GTK app: window and its tabs of one or two panes (`window/tab.rs`, `window/split.rs`), sidebar, reader host, home page, vault store, editor, Today, git sync
crates/daftar/reader/ generated by `just web` from web/src -- never edit, not committed
web/src/              the reading view: markdown-it with Obsidian's syntax
data/                 the desktop entry and the icon
```

Keep logic in `daftar-core`: its tests run in a second and need no display. Each Rust file of the core is the port of one Swift file of `notes-mac/Sources/DaftarCore` (`task_line.rs` is `TaskLine.swift`), and its tests are the ports of that file's tests. Port the Swift tests with the code, by the same names in snake case, so the two suites can be compared.

`daftar-cli` is the third user of the core, beside the app and the tests. A command prints plain lines (`path:line` and a tab, then the rest) for `grep`, `fzf` and scripts; it writes a note only through `VaultEdits`, as the app does. `sync` and `status` use `daftar_core::Git`, the port of `Git.swift`, which runs the system `git` with `GIT_TERMINAL_PROMPT=0` and SSH in batch mode; its tests sync two clones of a bare remote in a temporary folder. `query` runs the Tasks plugin's language (`tasks_query.rs`, `task_expression.rs`) on arguments, stdin or a note's ` ```tasks ` blocks, in callouts too; a line it does not understand goes to stderr. `sections.rs` is the outline's rules, the port of `Sections.swift`: a heading's children, the headings shown when some are closed (`level:text` keys, kept in `ReadingPlaces::closed`), sorting the headings under one and moving a section among its siblings. The app's inspector, `sort-headings` and the TUI's outline all use it. `tui/` is `daftar-cli tui` (ratatui on crossterm, so it runs on Windows too): `app.rs` holds the state with no terminal and is tested on a synthetic vault with `TestBackend`, `markdown.rs` turns a note into styled rows, `render.rs` draws and records where each pane went, `keys.rs` maps keys, `mouse.rs` maps clicks and the wheel through those areas, `watch.rs` watches the vault (`notify`, gathered until 300 ms quiet), `theme.rs` has the colors of `web/src/reader.css` (change them together). A full read of the vault (launch, `r`, after `s`) runs on a worker thread and comes back over a channel that the loop polls; a file the watcher reports meanwhile is read again on top of the result. `DAFTAR_TUI_VAULT=~/org cargo test -p daftar-cli -- --ignored` draws every note of a real vault, read-only. `clip` and the app's Clip Web Page share `daftar_core::web_fetch` (the core's `web` feature, `ureq` with rustls); `web_clip.rs` is the extraction, with no network. `images.rs` is the port of `notes-cli` (Python), which is archived: its markdown tests are ported by the same names. It never removes a picture a note mentions anywhere, in any form. `lint` is `daftar_core::MarkdownLint` (`markdown_lint.rs`), markdownlint-cli2's rules in Rust with no Node: it reads the vault's `.markdownlint.jsonc` and `.markdownlintignore`, knows Obsidian's syntax (wikilinks, embeds, callouts, tags, `$…$`), and its findings were checked against markdownlint-cli2 0.23 on fuzzed notes; a rule change must keep that agreement. `fmt` is `daftar_core::MarkdownFormat` (`markdown_format.rs`, with `yaml_format.rs` for the front matter and `string_width.rs` for table columns), Prettier 3.9's Markdown printer ported function by function onto `markdown-rs`'s tree; where markdown-rs and micromark disagree (a text that opens with an escape, a list item's end, an empty item under a paragraph, a symbol beside `*`/`_`) `parse` mends the tree, and wiki links and liquid tags are found after a first parse and hidden from a second. `tests/format_corpus.rs` compares it with Prettier on a folder of notes and their Prettier output, with `DAFTAR_FMT_CORPUS`; keep it at zero differences on a real vault and on that vault unformatted at random. `check` (`check.rs`) is the vault's audit: missing embeds and anchors (with the heading it likely meant), dangling and ambiguous links, links in code spans, callouts, task dates, badly written web addresses, unused pictures; `--urls` asks each address (`web_fetch::answers`, opt-in, never in a vault's CI) and `--archive` the Wayback Machine (`web_fetch::archived`, two at a time, waiting out a 429). `--fix` mends what has one answer, through `VaultEdits`: an ambiguous `[[Name]]` gets the shortest path to the note it went to, showing the same text, and with `--archive` a dead address its copy; `--dry-run` writes nothing. The vault's own `just fix` and `just check` run these, and its CLAUDE.md tells agents to rely on them instead of checking by hand: a change to what `lint`, `fmt` or `check` find is a change to that contract. `toggle`, `set-status`, `cancel` (with `--reason`) and `statuses` are the task commands; a status is one of the vault's (`TaskStatuses::load`).

## Adding a feature

1. If more than one app will have it, write the spec first in `docs/specs/` (Markdown format, reading, writing, what changes it, how it is shown, queries, and the test cases every app must have) and add it to the table in `docs/specs/README.md`. Build each app against that text, not against another app's code.
2. Put the rule in `daftar-core` with its tests, by the same names as the Mac's (`notes-mac/Sources/DaftarCore`), then the CLI command, then the GTK app. A new setting gets a line in `ConfigFile::TEMPLATE` here and in the Mac's template.
3. Run `just lint` and `just test` before a commit. The lints are `[workspace.lints]` in `Cargo.toml`, which every crate takes: rustc's extras and Clippy's pedantic group on the latest stable Rust, each lint left out there with why. In code, a lint is let off only with `#[expect(..., reason = "…")]`, never a bare `allow`, so one that stops firing says so. The GTK app needs a display: on a machine without one, build and run it under Xvfb (in a container with GTK 4, libadwaita and WebKitGTK 6.0), on a synthetic vault.
4. Commit straight to `main` and push, with no feature branch or pull request, once `just lint` and `just test` pass. Release when the work is in: here `just release X.Y.Z`, then `just aur` once the release's binaries are up.
5. A change to `web/src` is made in `notes-mac/web` and copied here (see below).

## The editor

`editor.rs` keeps the file rule (`write_if_unchanged`) and puts the core's editing rules on the keys: `EditorCommands`, `MarkdownTable`, `QuickSwitcher` for `[[`. Offsets are characters in the core and in GtkTextBuffer alike. Its colors are `MarkdownHighlighter` spans as GtkTextTags (`editor_style.rs`, the Mac's `NSPalette`), not GtkSourceView's markdown: a change styles its paragraph again, and only a change to a block line (a fence, the front matter, `$$`, `%%`) styles the rest. Its key controller runs in the capture phase, before the text view's own. A picture a line embeds is a `gtk::Picture` overlay of the view, never a character of the buffer: the line gets a tag whose `pixels-below-lines` is the picture's height, and the picture is placed in that space at idle priority LOW, after the view has laid the lines out (`editor_media.rs`). The view does not give an overlay child back (`TextView::remove` leaves it), so spare pictures are hidden and reused; and tags must not change while the view lays itself out (`gtk_text_view_validate_onscreen` aborts), so a width change refreshes from an idle. A picture is a `media::Loaded`: an SVG is drawn at twice its size, a GIF is a `PixbufAnimation` played by a tick callback (`media::play`) that is removed when the picture is put away; a click opens `picture_viewer.rs`, the GTK twin of the reader's `zoom()` (zoom is the picture's size request in a `ScrolledWindow`, `ContentFit::ScaleDown` at the fit of a photo, an SVG redrawn at each zoom), with the same keys. Change the two together. In Neovim mode (`neovim_session.rs`) a worker thread owns `NeovimClient`, whose `request` blocks, and the view never edits its own text: the buffer refuses an insert or a delete that is not Neovim's. So a command that edits the note (Sort Tasks, Sort Headings Under This, an outline move) checks `Editor::is_neovim` and goes through the file instead: it saves (Neovim writes), writes the file, and calls `changed_on_disk`. `check_disk` turns `autoread` on for its `checktime`, which reads nothing without it, and Neovim detaches a buffer it reads again (`nvim_buf_detach_event`), so the notification thread attaches anew with `send_buffer`, whose first lines event replaces the whole mirror. Neovim attaches with `ext_multigrid`: the notification thread keeps the grids in `vim_floats::FloatState` and sends `Event::Floats` at a `flush` that changed a float; the editor draws them as markup labels on `stage`, the overlay over the text. Persian in Neovim mode: `keyboard_langmap` sets `langmap` from the keyboard's layouts (unless the person's config has one), a `:` command takes the Latin keys of the Persian layout (`latin_key`), and the arrows swap on a right-to-left line. Live preview hides marks with a tag of next-to-no size and no color that must stay the top tag (`Styler::tag` raises it); never `invisible`, which aborts GTK ("byte index off the end of the line") when it lays out a long note whose lines end in hidden marks. A note is styled where it is seen: the first part when it opens, then the parts on screen and one above and below as it scrolls (`Styler::style_seen`, from a timeout, since GTK lays a long note out in idles above ours for seconds), each from `MarkdownHighlighter::block_state` at its start; `unstyled` holds the rest and moves with inserts and deletes. Every part tagged is laid out by GTK again, so styling a 2 MB note all at once cost 20 s of CPU more than GTK's own 14 s first layout. A part is styled with `MarkdownHighlighter::spans_of_lines`, reading only that part's text from the buffer: a change restyles its lines and at most `PARAGRAPH_LINES` around them, and the cursor's line is found by the buffer's line index, never by copying the note; GtkTextView takes a paragraph's direction from its first strong letter whatever a tag says, so a line whose syntax starts Latin and whose text is Persian is only right-justified (`flip`).

## The reader is shared with the Mac

`web/` is a copy of `notes-mac/web/`. The page talks to its host through `window.webkit.messageHandlers`, which WebKitGTK has as WKWebView does, so it runs unchanged. A change to `web/src` belongs in both repositories; keep the two copies the same, and keep a Linux-only need in the host, not in the page.

The host's side of the protocol, in `reader.rs`: the app calls `daftar.show(note)` with `{path, title, text, links, properties, keepScroll, textSize, fontText, fontCode}`, a note's `folds` (from `PlaceBook`) and `detected` (`detected.rs`), a base's `base` or a canvas's `canvas` (`canvas.rs`), and `heading` or `line`; the page posts `ready`, `open`, `toggleTask`, `tag`, `copy`, `external`, `detected`, `folds`, `edit`, `editTask`, `cursor`, `section` and `stopSpeaking` to `daftar`, and asks `embed`, `tasks` and `base`, which answer with a reply. `section` has no use here yet; `stopSpeaking` stops read aloud (`read_aloud.rs`), which asks the page for `daftar.speechBlocks()` and marks each with `daftar.speaking(index)`. `edit` sets the shown line and runs `win.edit`. To bring the Mac's page over, copy `web/src` and `web/test` (not `quicklook.js`), then put back the Linux lines: a new tab on Ctrl as well as ⌘, and the middle click.

A folder's overview is the reader's request for `Folder/` (a trailing slash): `FolderOverview::base` makes a base from its notes' properties and the reader runs it as a `.base`. Bases are `yaml.rs`, `base_expression.rs` and `bases.rs` (`YAML.swift`, `BaseExpression.swift`, `Bases.swift`). A `BaseEngine` is for one run; `BaseEngine::on_disk` reads `.obsidian/types.json` and the files' dates from the vault, and a creation date the file system does not keep is the change date. A regular expression is the `regex` crate's, which has no lookaround: one that does not compile makes its statement a listed problem, never a crash. Sorting goes through `safe_sort`, which cannot panic on an order that mixes kinds.

## Toolchain traps

- **The machine this was started on has no GTK.** The app is built and run in a container from `tools/Containerfile` (`podman build -t daftar-dev tools/`): Arch with GTK 4, libadwaita, WebKitGTK, Neovim, Xvfb and ImageMagick. Drive it with `xdotool` (`xdotool key ctrl+p`, `xdotool mousemove X Y click 1`); keep it running in a detached container (`podman run -d`) and `podman exec` each step, and stop it with `pkill -x daftar`, not `pkill -f`, which matches the shell that runs it. Run the app under `Xvfb` with `GDK_BACKEND=x11` and `dbus-run-session` (WebKit finds that bubblewrap cannot run in the container and goes without it; no variable is needed), and look at it with `import -window root shot.png`. Point it at a synthetic vault with `XDG_CONFIG_HOME` and a `config.toml` that says `vault = "/vault"`.
- **`evaluate_javascript` fails on a promise** (`Unsupported result type`): a script that calls an async function ends with `; undefined`.
- **A web view taken out of the window spins the main loop** (100% CPU, no more input). A closed split hides its pane and keeps it in `Group::spare` for the next split instead of removing it (`window/split.rs`). A pane's `gtk::Stack` is not `hhomogeneous`, or the board's width would be every page's minimum and a split pane would be drawn clipped.
- **A handler that opens a note must not run inside a `RefCell` borrow.** Opening a note borrows the reader's state, the window's recent list and its tabs again, and a panic in a GTK or WebKit callback aborts the app. Take a handler or a list out of its cell (`let handler = cell.borrow().x.clone();`) before calling it, and bind `self.tabs.borrow().clone()` to a name before a `for` loop: a temporary in the loop's head, or in an `if let` condition, lives to the end of the block.
- **A URI scheme belongs to the web context, which every window shares.** `register_schemes` runs once; the `vault:` scheme finds the open vault through `VAULT_ROOT`.
- **WebKit draws no frame for a page that changes under a closing dialog.** The palette opens the picked note in the dialog's `closed` handler, not before `close()`.
- **`include_dir!` needs `crates/daftar/reader/` at compile time.** Run `just web` before `cargo build`; every `just` recipe that builds does.

## Rules the code keeps

- **Every setting is in one file, `~/.config/daftar/config.toml`** (`$XDG_CONFIG_HOME` is honoured), the same file Daftar for macOS reads, so a dotfiles repository can carry one copy for both. A key means the same thing in both apps; a key one app does not have is left alone by it. `ConfigFile` reads a small TOML subset and writes a changed value on its own line, keeping the person's comments. A new setting gets a line in `ConfigFile::TEMPLATE` here and in `ConfigFile.template` on the Mac.
- **An edit reads the file again and refuses when the line changed.** `VaultEdits::toggle_task` checks that the clicked line is still a task with the status the page showed. Never write from what the view or the index remembers. A write goes through a temporary file and a rename.
- **The index is in memory and is built at launch**, away from the main thread (`gio::spawn_blocking`). The files are the record; there is no database on disk to migrate. `watcher.rs` (inotify, the Mac's `FileWatcher`) reports the vault paths that changed, gathered for 200 ms, and only ones `Vault::counts`; `Window::files_changed` updates the index and search, rebuilds the tree only when files came or went (open folders stay open), and draws the note on screen again when it or a note it links to changed.
- **The reader page reaches nothing but two schemes:** `daftar://reader/…` (built into the binary) and `vault:///…` (the vault, and nothing outside it: `store::file_in` refuses `..`, absolute paths and symlinks out). The page has a content security policy; keep `script-src 'self'`. A page or an SVG from the vault is served with a `sandbox` policy. The window never leaves `daftar://reader/`.
- **Links leave the app as web, mail and phone links only** (`OUTSIDE` in `reader.rs`: `http`, `https`, `mailto`, `tel`, `sms`, `geo`), through `gtk::UriLauncher`. A detected address opens OpenStreetMap's search over https.
- **A sync never commits over an open rebase.** A pull that stops on a conflict is `SyncFailure::Stopped` and leaves the rebase open (`rebase-merge` or `rebase-apply`); `Git::sync` and `Git::pull` refuse while one is open, and `GitSync` stops every sync until the person finishes or aborts in `conflicts.rs`. In a rebase git's "ours" is the upstream and "theirs" is the person's commit: say "On the remote" and "Your change", never ours and theirs. `rebase --continue` runs with `GIT_EDITOR=true`, in a loop, since the next replayed commit can stop too. `conflict_text.rs` parses and resolves the marks, to the byte when nothing is chosen.
- **A note's history is `git log --follow`** (`Git::history`), and a restore is an ordinary write: the next sync commits it, so nothing in the history is lost.
- **Quick capture works with no window of notes.** `daftar --capture` registers the application: in a running Daftar it activates `app.capture` there and exits; else it is the app, with only the capture window. `QuickCapture::capture` (core) reads the file again at the write and keeps every line; the CLI's `capture` is the same call.
- **The week notes in `Calendar/` are read-only here.** The phone writes them whole at every change.
- **Colors are Daftar's:** naz on dark, Daylight on light, in `web/src/reader.css`; the window follows `appearance.theme` through `adw::StyleManager`, and the page follows the window.
- **The app id is `me.parham1995.notes`**, the Mac app's bundle id, for the desktop entry, the icon and the window class.

## Testing the app

**Do not click a task in the real vault to test.** A tick writes the file. Test writes on a copy, or with the unit tests.

`just release 0.2.0` sets VERSION and the crate versions, commits, tags and pushes; CI checks the tag matches VERSION, builds the CLI for every OS and publishes the release. The `daftar-cli` formula in parham-alvani/homebrew-tap follows releases with a daily bump job that also runs the tap's CI, or at once with `gh workflow run bump.yaml -R parham-alvani/homebrew-tap`. `just aur` then moves the AUR packages `daftar-bin` and `daftar-cli-bin` to VERSION, pushes them with your AUR SSH key, and commits the new `PKGBUILD`s here; the AUR's search API may show the old version for a while after.
