# CLAUDE.md

Guidance for Claude Code in this repository.

## What this is

**Daftar for Linux**: a native Rust app (GTK 4, libadwaita, WebKitGTK 6.0) for an Obsidian vault in a Git repository, meant to replace Obsidian on a Linux desktop, a tiling Wayland compositor first. It is the sister of `notes-mac` (Daftar for macOS, Swift) and `notes-droid` (Daftar for Android, Kotlin). The three apps share no code, but they share rules: how a wikilink resolves, what a task line is and how it is ticked, the task statuses (`task_status.rs`, from `[tasks.statuses.*]` in the vault's `.daftar.toml`, else the Tasks plugin's settings) and the `[reason:: …]` field (`TaskReason` in `task_line.rs`): a reason goes with the status it was given with, the format of the week notes in `Calendar/`, the config file and the colors. When a rule changes in one, change it in the others. A rule more than one app keeps is written down in `docs/specs/` (see [Adding a feature](#adding-a-feature)). A lesson that holds for any desktop app (a trap of GTK, libadwaita or WebKitGTK, a data-safety rule, a way to measure) also goes into the `taller` plugin for Claude Code, which gathers the three apps' lessons, with its reason and commit; this file keeps what is about this app.

The repository is **public**; the vault it reads is private. Every test fixture is synthetic.

## Commands: always `just`

```bash
just test     # cargo test + node --test for the renderer
just lint     # cargo fmt --check + clippy -D warnings, as CI runs them, with the lints of [workspace.lints]
just run      # build and start; `just run Notes/Inbox.md` opens that note
just cli …    # the command line on the configured vault: `just cli tasks --due today`
just app      # the release binary
just web      # rebuild the reader bundle only
just install  # ~/.local/bin/daftar, its desktop entry and icon
just bench    # the core on a made-up vault of 20,000 notes, timed (crates/daftar-core/tests/bench.rs)
```

## Layout

```text
crates/daftar-core/   no GTK: parser, link resolver, tasks, index, search, config
crates/daftar-cli/    `daftar-cli`: the core on the command line, and notes-cli's picture cleanup
crates/daftar/        the GTK app: window and its tabs of one or two panes (`window/tab.rs`, `window/split.rs`), sidebar, reader host, home page, vault store, editor, Today, git sync
crates/daftar/reader/ generated by `just web` from web/src -- never edit, not committed
web/src/              the reading view: markdown-it with Obsidian's syntax
data/                 the desktop entry and the icon
```

Each Rust file of the core is the port of one Swift file of `notes-mac/Sources/DaftarCore` (`task_line.rs` is `TaskLine.swift`), and its tests are the ports of that file's tests. ## Adding a feature

1. If more than one app will have it, write the spec first in `docs/specs/` (Markdown format, reading, writing, what changes it, how it is shown, queries, and the test cases every app must have) and add it to the table in `docs/specs/README.md`. Build each app against that text, not against another app's code.
2. Put the rule in `daftar-core` with its tests, by the same names as the Mac's (`notes-mac/Sources/DaftarCore`), then the CLI command, then the GTK app. A new setting gets a line in `ConfigFile::TEMPLATE` here and in the Mac's template.
3. Run `just lint` and `just test` before a commit. The lints are `[workspace.lints]` in `Cargo.toml`, which every crate takes: rustc's extras and Clippy's pedantic group on the latest stable Rust, each lint left out there with why. In code, a lint is let off only with `#[expect(..., reason = "…")]`, never a bare `allow`, so one that stops firing says so. The GTK app needs a display: on a machine without one, build and run it under Xvfb (in a container with GTK 4, libadwaita and WebKitGTK 6.0), on a synthetic vault.
4. Commit straight to `main` and push, with no feature branch or pull request, once `just lint` and `just test` pass. Release when the work is in: here `just release X.Y.Z`; the tag's CI does the rest.
5. A change to `web/src` is made in `notes-mac/web` and copied here (see below).

## The editor

`editor.rs` keeps the file rule (`write_if_unchanged`) and puts the core's editing rules on the keys: `EditorCommands`, `MarkdownTable`, `QuickSwitcher` for `[[`. Offsets are characters in the core and in GtkTextBuffer alike. Its colors are `MarkdownHighlighter` spans as GtkTextTags (`editor_style.rs`, the Mac's `NSPalette`), not GtkSourceView's markdown: a change styles its paragraph again, and only a change to a block line (a fence, the front matter, `$$`, `%%`) styles the rest. Its key controller runs in the capture phase, before the text view's own. A picture a line embeds is a `gtk::Picture` overlay of the view, never a character of the buffer: the line gets a tag whose `pixels-below-lines` is the picture's height, and the picture is placed in that space at idle priority LOW, after the view has laid the lines out (`editor_media.rs`). The view does not give an overlay child back (`TextView::remove` leaves it), so spare pictures are hidden and reused; and tags must not change while the view lays itself out (`gtk_text_view_validate_onscreen` aborts), so a width change refreshes from an idle. A picture is a `media::Loaded`: an SVG is drawn at twice its size, a GIF is a `PixbufAnimation` played by a tick callback (`media::play`) that is removed when the picture is put away; a click opens `picture_viewer.rs`, the GTK twin of the reader's `zoom()` (zoom is the picture's size request in a `ScrolledWindow`, `ContentFit::ScaleDown` at the fit of a photo, an SVG redrawn at each zoom), with the same keys. Change the two together. In Neovim mode (`neovim_session.rs`) a worker thread owns `NeovimClient`, whose `request` blocks, and the view never edits its own text: the buffer refuses an insert or a delete that is not Neovim's. So a command that edits the note (Sort Tasks, Sort Headings Under This, an outline move) checks `Editor::is_neovim` and goes through the file instead: it saves (Neovim writes), writes the file, and calls `changed_on_disk`. `check_disk` turns `autoread` on for its `checktime`, which reads nothing without it, and Neovim detaches a buffer it reads again (`nvim_buf_detach_event`), so the notification thread attaches anew with `send_buffer`, whose first lines event replaces the whole mirror. Neovim attaches with `ext_multigrid`: the notification thread keeps the grids in `vim_floats::FloatState` and sends `Event::Floats` at a `flush` that changed a float; the editor draws them as markup labels on `stage`, the overlay over the text. Persian in Neovim mode: `keyboard_langmap` sets `langmap` from the keyboard's layouts (unless the person's config has one), a `:` command takes the Latin keys of the Persian layout (`latin_key`), and the arrows swap on a right-to-left line. Live preview hides marks with a tag of next-to-no size and no color that must stay the top tag (`Styler::tag` raises it); never `invisible`, which aborts GTK ("byte index off the end of the line") when it lays out a long note whose lines end in hidden marks. A note is styled where it is seen: the first part when it opens, then the parts on screen and one above and below as it scrolls (`Styler::style_seen`, from a timeout, since GTK lays a long note out in idles above ours for seconds), each from `MarkdownHighlighter::block_state` at its start; `unstyled` holds the rest and moves with inserts and deletes. Every part tagged is laid out by GTK again, so styling a 2 MB note all at once cost 20 s of CPU more than GTK's own 14 s first layout. Live preview also draws parts of the note (`docs/specs/look.md`, part 2), and the rules of what is drawn are the core's `LivePreview` (`live_preview.rs`): a task's box, the date chips, a callout's panel and a code block's panel, each a way to see the text and never a character of the buffer. GtkTextView draws only text and the backgrounds of tags, so the view is a subclass, `EditorView` (`editor_view.rs`), whose `snapshot_layer` hands both layers to `Draw` (`editor_draw.rs`): panels and pills under the text, boxes and icons over it, each found among the lines on screen by the tag `Styler::draw_parts` put on its text (`Styler::drawn` lists those tags), so nothing is kept beside the buffer and nothing walks the note. The icons are the reader's, read from `tasks.css` and `callouts.css` of the bundle by their Lucide name and drawn as a mask. The width a drawn part needs is letter spacing on its hidden marks (1.1 em for a box, the room around a chip in the spaces beside it), a panel's room is the left and right margin of its lines' tag, and a look that hangs on the text size or the measure is worked out from `Metrics` in `apply_look`. Traps: a foreground with no alpha at all is drawn solid, so a clear mark has a little (`CLEAR`); `iter_location` of a hidden mark has next to no height, so a box takes its row from the space after it; a view with `cursor-visible` off scrolls on the arrow keys instead of moving the cursor, so GTK's caret is hidden by `caret-color: transparent` (`style.rs`) and `Caret` (`editor_caret.rs`) draws the accent one in the same layer, at the place the view gives when it draws, which is after the lines are laid out. The editor's line is the measure (`Editor::measure`): the view fills the pane and its left and right margins are the room `LivePreview::measure` gives, set from an idle when the pane's width changes and when the settings do. A part is styled with `MarkdownHighlighter::spans_of_lines`, reading only that part's text from the buffer: a change restyles its lines and at most `PARAGRAPH_LINES` around them, and the cursor's line is found by the buffer's line index, never by copying the note; GtkTextView takes a paragraph's direction from its first strong letter whatever a tag says, so a line whose syntax starts Latin and whose text is Persian is only right-justified (`flip`). A table with its delimiter row is a grid (`LivePreview::grid_lines` on `MarkdownTable::is_grid`): GtkTextView has no cells, so its rows stay text in the code font, lined up by the formatter's spaces, and the grid is tags and a drawing. `Styler::draw_grid` makes each pipe clear, the delimiter row next to no height (Up and Down pass over it) and the rows stand one on the other; `pad_grid` gives a cell back, after its last space, the width its hidden marks and its smaller letters lost, so the columns stay in line; `Draw::grid` draws the box, the header's fill and a hairline where each pipe stands. A row styled alone reads the rows above and under it from the buffer (`rows_beside`), a table wider than the measure is no grid (`Metrics::fits`), and the table that shows raw (a selection out of one cell, the caret on the delimiter row) is kept in `raw_tables` and followed in `reveal`. Tab, Shift+Tab, Return and Shift+Return in a table are the core's `MarkdownTable::tab_key` and `return_key` on the note's text (`table_key`), each one `replace`, so one step to undo: the table is the run of lines that start with a pipe (`MarkdownTable::block`), never a line beside it, a selection in one cell moves as its caret, and a header cell that still reads `Column` is selected whole. The slash bar (`editor_slash.rs`) is a popover that never has the focus: `on_char` only notes where a `/` was typed, and the restyle's idle opens the bar once the `/` is in the text (`EditorCommands::slash_bar_opens`, the one place that reads the note for its block state, on a `/` only); `key` sends it Up, Down, Ctrl+N, Ctrl+P, Return, Tab and Escape before anything else. A picked item is `EditorCommands::apply_over` on the whole note: a block that stands apart (`Snippet::stands_apart`: a callout, a fence, math, a table, the rule) gets a blank line between it and a line with text on either side, since without one the reader and format on save take the next paragraph as a row, a callout's body or a heading over the rule; only line breaks are added, and the Table item's first `Column` is selected. Focus mode (`editor_focus.rs`) lays no tag: `Focus` keeps the bright paragraph as two marks of the buffer (`FocusParagraph::lines`, asked of the buffer's lines), looks at it again only on the lines a change touched, and paints a veil in the page's colour over the rest, in the layer over the text and under the caret. The link preview (`editor_link_card.rs`) finds the `[[link]]` under the pointer on the line's text (`LinkPreview::link_at`) and shows `LinkPreview::card` in a popover whose body is a second `EditorView` with its own `Styler` and `Draw`, so the lines look as the editor draws them. Popover traps: GTK sizes a popover when it is shown or its parent is allocated, not when what it holds changes, so a list or a card that grows calls `Popover::present`; GTK closes a popover whose least size grows while it is on screen, so the card's view only says the height it would like (`EditorView::set_natural_height`); and under X with no compositor the popover's surface, shadow and all, takes the pointer from the view (the view hears a leave while the pointer is still on the link), so the card asks where the pointer is before it closes (`pointer_on_shown_link`). A mark's element (`Span::owner`) must be put in the styled part's own characters with its range, or the marks of an element never show with the caret in it. An edit before the cursor moves the cursor's place and sets no mark (a click on a box above it, Format Note, Neovim's lines), so `restyle_after` reads the place again first (`Styler::follow_edit`): styled against the old place, an element across it made an offset under zero, which aborts a debug build. A `|` line in a code block, the front matter, math or a comment is no table (`MarkdownTable::block` asks `MarkdownHighlighter::block_state`), so Tab and Return never format code.

## New Task and the switch between reading and editing

New Task (`win.new-task`, Ctrl+Alt+T, the palette) is `task_edit::present_new`: the Edit Task form with a Note (a searchable list, notes with tasks first) and a Section, for the note on screen and the heading its cursor or reading place is under (today's scratchpad with no note), and today as its ➕ created date. `TaskLine::written` makes the line and `VaultStore::add_task` puts it at the end of that heading's section with `QuickCapture::append_at_heading_line`, after `save_editors`, reading the file again (`docs/specs/new-task.md`). The form's Created row edits ➕ on any task.

Ctrl+E goes by one line both ways: into the editor at the reading place (`store.places`, which the reading cursor keeps), not at the line the note was opened at; back to reading, the editor's line becomes the reading place. Both ways are the soft change of `docs/specs/look.md` (`SoftChange` in `reader.rs`): 120 ms, at the same line, the keys with the view that comes from the start. Between two notes the change is the page's (`softly` in `web/src/reader.js`), and until the page has drawn the new note it takes no click and no plain key (`leaving`): the app already has the new note, and a task's box names its line with no path, so a click on the note that leaves would tick that line of the new one. Into the editor, the pane's stack crossfades (its `transition_duration` is `SoftChange::FADE`). Back to reading, the reader is on screen and has the focus at once, under a picture of the editor (`SoftChange::picture`, a `gtk::WidgetPaintable`'s image taken before the editor lets its note go, drawn in `Reader::page`, the `gtk::Overlay` that holds the web view); `Reader::show_under` fades the picture out once the page has drawn the note at the editor's line (`Reader::show_then`, which awaits `daftar.show` with `call_async_javascript_function`), or after 400 ms. Seen before it had drawn, the page was at its old place and jumped. Without `gtk-enable-animations` the picture goes at once, with no fade. A window holds `reader.page`, never `reader.view` alone.

## The reader is shared with the Mac

The reading cursor is a block with a band on one line of it (`reading` in `web/src/reader.js`, the Mac's 0.12.0): a block's lines are its text's rects merged where they share most of their height (`rows`), `j`/`k` go a line at a time, the file line of a line (`sourceLine`) is the block's line plus the `\n` before it, found with `caretRangeFromPoint`, and after a scroll a cursor off screen comes to the first line on screen (`follow`). `appearance.reading_line` is the band's strength, sent as `readingLine`; 0 is none.

`web/` is a copy of `notes-mac/web/`. The page talks to its host through `window.webkit.messageHandlers`, which WebKitGTK has as WKWebView does, so it runs unchanged. A change to `web/src` belongs in both repositories; keep the two copies the same, and keep a Linux-only need in the host, not in the page.

The host's side of the protocol, in `reader.rs`: the app calls `daftar.show(note)` with `{path, title, text, links, properties, keepScroll, textSize, fontText, fontCode}`, `linkPreview` and `sectionBar` (`appearance.link_preview`, `appearance.section_bar`), a note's `folds` (from `PlaceBook`: the sections the person left shut, or `null` when they set none) with `folded` (whether notes open folded: `appearance.fold_sections` with the vault's `reader.folded`, `vault_settings.rs`, read from `.daftar.toml` at each show; with no list kept the page shuts every section, and a folded heading says what it holds, `docs/specs/folded-sections.md`) and `detected` (`detected.rs`), a base's `base` or a canvas's `canvas` (`canvas.rs`), and `heading` or `line`; the page posts `ready`, `open`, `toggleTask`, `tag`, `copy`, `external`, `detected`, `folds`, `edit`, `editTask`, `cursor`, `section` and `stopSpeaking` to `daftar`, and asks `embed`, `preview`, `tasks` and `base`, which answer with a reply. Every message posted to `daftar` carries `note`, the path of the note the page has drawn (`onPage`): the host drops every message but `ready` whose `note` is not the path of the note it shows (`hears` in `reader.rs`, as the Mac's `ReaderView.Coordinator` does), since a page that was busy when the app took the next note can still click on the note that leaves, before `leaving` gates it, and a task's box names its line with no path: that click ticked the line in the new note's file. A message with no `note` is dropped too, as the page is built into the binary and `post` always names one. This is by state, never by a delay; the display test's `a_click_the_page_made_before_it_heard_of_the_next_note_ticks_nothing` clicks before the page hears of the next note. The questions with a reply (`embed`, `preview`, `tasks`, `base`) write nothing and carry no `note`. `preview` is a link's card: `{path, anchor}` is answered with `{title, text, links}`, where `text` is only the first lines (`LinkPreview::excerpt` in the core's `link_preview.rs`, the port of `LinkPreview.swift`), or with null for a file that is no note of the vault; a page with no `preview` handler asks `embed`. `section` has no use here yet; `stopSpeaking` stops read aloud (`read_aloud.rs`), which asks the page for `daftar.speechBlocks()` and marks each with `daftar.speaking(index)`. `edit` sets the shown line and runs `win.edit`. To bring the Mac's page over, copy `web/src` and `web/test` (not `quicklook.js` and its test), then put back the Linux lines: a new tab on Ctrl as well as ⌘, and the middle click. `diff -r web/src ../notes-mac/web/src` then shows those lines and `quicklook.js` alone.

A folder's overview is the reader's request for `Folder/` (a trailing slash): `FolderOverview::base` makes a base from its notes' properties and the reader runs it as a `.base`. Bases are `yaml.rs`, `base_expression.rs` and `bases.rs` (`YAML.swift`, `BaseExpression.swift`, `Bases.swift`). A `BaseEngine` is for one run; `BaseEngine::on_disk` reads the property types (`[properties.types]` of `.daftar.toml`, else `.obsidian/types.json`) and the files' dates from the vault, and a creation date the file system does not keep is the change date. A regular expression is the `regex` crate's, which has no lookaround: one that does not compile makes its statement a listed problem, never a crash. Sorting goes through `safe_sort`, which cannot panic on an order that mixes kinds.

## Toolchain traps

- **The machine this was started on has no GTK.** The app is built and run in a container from `tools/Containerfile` (`podman build -t daftar-dev tools/`): Arch with GTK 4, libadwaita, WebKitGTK, Neovim, Xvfb and ImageMagick. Drive it with `xdotool` (`xdotool key ctrl+p`, `xdotool mousemove X Y click 1`); keep it running in a detached container (`podman run -d`) and `podman exec` each step, and stop it with `pkill -x daftar`, not `pkill -f`, which matches the shell that runs it. Run the app under `Xvfb` with `GDK_BACKEND=x11` and `dbus-run-session` (WebKit finds that bubblewrap cannot run in the container and goes without it; no variable is needed), and look at it with `import -window root shot.png`. Point it at a synthetic vault with `XDG_CONFIG_HOME` and a `config.toml` that says `vault = "/vault"`.
- **`evaluate_javascript` fails on a promise** (`Unsupported result type`): a script that calls an async function ends with `; undefined`.
- **A web view taken out of the window spins the main loop** (100% CPU, no more input). A closed split hides its pane and keeps it in `Group::spare` for the next split instead of removing it (`window/split.rs`). A pane's `gtk::Stack` is not `hhomogeneous`, or the board's width would be every page's minimum and a split pane would be drawn clipped.
- **A handler that opens a note must not run inside a `RefCell` borrow.** Opening a note borrows the reader's state, the window's recent list and its tabs again, and a panic in a GTK or WebKit callback aborts the app. Take a handler or a list out of its cell (`let handler = cell.borrow().x.clone();`) before calling it, and bind `self.tabs.borrow().clone()` to a name before a `for` loop: a temporary in the loop's head, or in an `if let` condition, lives to the end of the block.
- **A URI scheme belongs to the web context, which every window shares.** `register_schemes` runs once; the `vault:` scheme finds the open vault through `VAULT_ROOT`.
- **WebKit draws no frame for a page that changes under a closing dialog.** The palette opens the picked note in the dialog's `closed` handler, not before `close()`.
- **`include_dir!` needs `crates/daftar/reader/` at compile time.** Run `just web` before `cargo build`; every `just` recipe that builds does.

## Rules the code keeps

- **Every setting is in one file, `~/.config/daftar/config.toml`** (`$XDG_CONFIG_HOME` is honoured), the same file Daftar for macOS reads, so a dotfiles repository can carry one copy for both. A key means the same thing in both apps; a key one app does not have is left alone by it. `ConfigFile` reads a small TOML subset and writes a changed value on its own line, keeping the person's comments. A new setting gets a line in `ConfigFile::TEMPLATE` here and in `ConfigFile.template` on the Mac.
- **An edit reads the file again and refuses when the line changed.** `VaultEdits::toggle_task` checks that the clicked line is still a task with the status the page showed. Never write from what the view or the index remembers. A write goes through a temporary file and a rename.
- **The index is in memory and is built at launch**, away from the main thread (`gio::spawn_blocking`). The files are the record; there is no database on disk to migrate. `watcher.rs` (inotify, the Mac's `FileWatcher`) reports the vault paths that changed, gathered for 200 ms, and only ones `Vault::counts`; `Window::files_changed` updates the index and search, rebuilds the tree only when files came or went (open folders stay open), and draws the note on screen again when it or a note it links to changed.
- **The reader page reaches nothing but two schemes:** `daftar://reader/…` (built into the binary) and `vault:///…` (the vault, and nothing outside it: `store::file_in` refuses `..`, absolute paths and symlinks out). The page has a content security policy; keep `script-src 'self'`. A page or an SVG from the vault is served with a `sandbox` policy. The window never leaves `daftar://reader/`.
- **Links leave the app as web, mail and phone links only** (`OUTSIDE` in `reader.rs`: `http`, `https`, `mailto`, `tel`, `sms`, `geo`), through `gtk::UriLauncher`. A detected address opens OpenStreetMap's search over https.
- **A read-only clone pulls and never writes** (`docs/specs/read-only-vault.md`). `daftar.readonly` in the clone's own git config (`Git::is_read_only`, never the global config; a value that is no boolean is read-only) makes `Git::sync` and `Git::pull` a `git pull --no-rebase --ff-only` that fails as `SyncFailure::ReadOnlyDiverged` with the files when the clone has commits or changes in the way, and every write of a vault file asks `VaultEdits::writable` first, before the file is read: `VaultEdits::apply`, `create` and `delete`, `QuickCapture::capture`, `VaultMoves::perform`, `WebClip::create`, `Bookmarks::save`, and in the app `files.rs`, `write_if_unchanged`, a pasted or dropped picture and Fix. `Git::read_only(root)` is the same answer kept by the clone's config file's change time, so a write asks git once. A new place that writes a vault file must ask too; a dry run goes through `VaultEdits::look`, which reads and writes nothing. `daftar-cli` refuses its writing commands at the top of `run` (`writes` in `main.rs`: a new writing command is added there and to the spec's list), `mcp` serves as with `--read-only`, or not at all when the vault's `.daftar.toml` says `[agents] read_only_clones = false` (`Door` in `mcp.rs`: every request is answered with the error and the server exits 1), `lsp` answers formatting and rename with no edit, and `hook pre-commit` refuses the commit. The window shows a Read-only badge by the vault's name, turns off `WRITING_ACTIONS` (a new action that writes is added there), and its sync button has Pull alone. A push refused for a key that cannot write is `SyncFailure::PushRefusedReadOnly` (`Git::push_refused_read_only`), and its notice offers Make This Vault Read-only.
- **The clone's key is kept.** `Git::ssh_command` is the `GIT_SSH_COMMAND` of every git Daftar runs: the person's own variable as it is, else the clone's `core.sshCommand` with `-o BatchMode=yes` added when it does not name it, else `ssh` with it. Settings › Vault · Git (`vault_git_group` in `preferences.rs`, only for a repository) writes the clone's own config with `git config --local`: `daftar.readonly`, the address (`Git::remote` is the remote of the branch's upstream, else `origin`; `Git::set_address`), `user.name`, `user.email`, and the key as `core.sshCommand` (`Git::ssh_command_for_key`; `Git::generate_key` runs `ssh-keygen`, never over a file).
- **The vault may set the app's settings, from a list** (`docs/specs/vault-config.md`). `Settings` (`settings.rs`, core) resolves the vault's `.daftar.toml` over the computer's `config.toml`: `ALLOWED` is every key a vault may set with what its value must be (the ranges are the spec's table, the same as the Mac's `ResolvedSettings.allowed`), a key under one of the app's `SECTIONS` that is not on it is refused by name (it names a program, a file outside the vault, or what leaves the computer), a value a key may not have is as not there, and `vault_settings` in `config.toml` declines all or some. A new setting that a vault may set gets its line in `ALLOWED` in the same change as its line in the template. A change made in the app to a key the vault sets holds until the settings are read again. The app's `AppSettings::file` and the CLI's `config(root)` are the settings in use (the computer's file with the vault's values set in it), so every reader of a setting follows the vault with no change. A change in the app goes where `Settings::write_target` says (section 5 of the spec): the device (`config.toml`) for a key or a value a vault may not hold, a key `vault_settings` declines, and every change while the vault cannot be written (`AppSettings::vault_writable`: a read-only clone, or no `.daftar.toml` in a folder that is no repository); the platform's table (`[linux.…]`, read over the shared sections, `Platform` in `settings.rs`) for a key it has already, the fonts, the terminal's size and `Platform::own_keys`; else the shared section. `ConfigFile::set` writes the one line in either file, and `AppSettings::set` reads both files again first and writes `.daftar.toml` through `VaultEdits`, so a read-only clone refuses it and the sync that follows an edit takes it; the settings it holds afterwards are the ones a re-read gives, so the file monitor's reload changes nothing. `vault`, `vaults` and `vault_settings` are never written to the vault. Settings shows a key the vault sets as "From the vault" (`from_vault`), off only where the vault cannot be written, and each row's context menu has Keep on This Device and Follow the Vault (`Settings::keep_on_device`, `follow_vault`). A setting only Linux has that a vault may hold is added to `Platform::own_keys` and to the README's list. The window follows `.daftar.toml` with a file monitor and reads it again after each sync. The author of a commit is the clone's own `user.name` and `user.email`, else the vault's `git.name` and `git.email` as `-c` options (`Git::author_options`), else git's. `daftar-cli config` lists every key with its value and where it came from, and `doctor` warns of a refused key (`vault-config-refused`).
- **A note with a `type` is a concept of the Open Knowledge Format** (`docs/specs/open-knowledge-format.md`, OKF 0.3). `Okf::concept` (`okf.rs`, core) reads the front matter with OKF's consumer rules and refuses nothing: the status (an unknown one is kept and is not stable), `stale_after` (a time that is none is stale), `generated` and the `verified` events, whose current ones (at or after `generated.at`) give the tier. `index.md` and `log.md` are never concepts. `Okf::mark_verified` (a block list, one `{ by, at }` a line) and `Okf::mark_generated` write one key of the front matter again and keep every other line byte for byte (`PropertySheet` holds no list of mappings). A Markdown link resolves in `LinkResolver::resolve_with` as OKF reads it: a `/` path from the bundle root (`Okf::bundle_roots`, set at each `VaultIndex::derive`), a `./` or `../` path from the note's folder, and one that climbs out of the vault names nothing; a move keeps the link's form. In the CLI, `check` with `okf` warns (`okf_problems` in `check.rs`), the MCP server has `concepts` and marks an agent's change to a concept's text (`apply_marked`, with the client of `initialize` as `Okf::producer`), and `okf.rs` is `okf export` and `okf check`: the export gathers every file of the bundle in memory (`bundle`), writes only the ones whose bytes changed and removes what an earlier run wrote, never in the vault and only in an empty folder or one whose root `index.md` has `x-daftar-export: true`. In the app, the inspector's Concept row (`concept_row` and `concept_chips` in `inspector.rs`) is above the properties, the reader's line is an `adw::Banner` over the web view in each pane (`Tab::concept_line`, set by `Window::show_concept_line` from `Concept::reader_line`; the page itself is not changed, so `web/` stays the Mac's), Mark as Verified is `win.mark-verified` (`VaultStore::mark_verified`, with `okf.actor` or the clone's `user.email` through `Okf::actor`), and the palette dims a deprecated concept (`Candidate::deprecated` puts it after the others of its rank).
- **A change of vault happens in the running app, and leaves nothing of the vault before** (`docs/specs/several-vaults.md`). `Vaults` (`vaults.rs`, core) is the list, pure over the text of `config.toml`: `vaults` beside `vault`, one folder however it is spelled, the vault in use always among them. `Window::switch_vault` (`window/vaults.rs`) is the one path for Switch Vault, Open Vault… and Settings › Vault: a missing folder is refused, every window's editors save (`vault_change::lets_go`; one that keeps its text stops the change), a sync that is running is waited for, this window's tabs are saved by the vault's folder (`vault_change::Tabs`), every window goes down to one empty tab, and each runs `load` for the new folder. `load` makes everything again through `vault_change::open`, which has no widget and is what `a_change_leaves_nothing_of_the_vault_before` tests: the settings the vault's `.daftar.toml` sets, the hidden files, the store with its index, search, bookmarks, icons, templates and daily notes, read-only, and `vault` and `vaults` in `config.toml` (written only on a change, never at a launch, and only once the change is not refused). The rest of `load` resets what the window holds: the watcher, the sync button (`GitSync::attach` drops the vault before's failure, conflicts and read-only menu), the Problems panel (`VaultChecks::opened`), the notifier's plan, the reader's `VAULT_ROOT` and its told notes (`Reader::set_store`), the inspector, each pane's history, pending note, concept line and voice. A new kind of state a window keeps for a vault is reset there, and asserted in that test when it has no widget. The windows are in `WINDOWS`, since one vault is open at a time in all of them.
- **A sync never commits over an open rebase.** A pull that stops on a conflict is `SyncFailure::Stopped` and leaves the rebase open (`rebase-merge` or `rebase-apply`); `Git::sync` and `Git::pull` refuse while one is open, and `GitSync` stops every sync until the person finishes or aborts in `conflicts.rs`. In a rebase git's "ours" is the upstream and "theirs" is the person's commit: say "On the remote" and "Your change", never ours and theirs. `rebase --continue` runs with `GIT_EDITOR=true`, in a loop, since the next replayed commit can stop too. `conflict_text.rs` parses and resolves the marks, to the byte when nothing is chosen.
- **A note's history is `git log --follow`** (`Git::history`), and a restore is an ordinary write: the next sync commits it, so nothing in the history is lost.
- **Quick capture works with no window of notes.** `daftar --capture` registers the application: in a running Daftar it activates `app.capture` there and exits; else it is the app, with only the capture window. `QuickCapture::capture` (core) reads the file again at the write and keeps every line; the CLI's `capture` is the same call.
- **The week notes in `Calendar/` are read-only here.** The phone writes them whole at every change.
- **Colors are Daftar's:** naz on dark, Daylight on light, in `web/src/reader.css`; the window follows `appearance.theme` through `adw::StyleManager`, and the page follows the window.
- **The app id is `me.parham1995.notes`**, the Mac app's bundle id, for the desktop entry, the icon and the window class.

## Testing the app

**Do not click a task in the real vault to test.** A tick writes the file. Test writes on a copy, or with the unit tests.

`just release 0.2.0` sets VERSION and the crate versions, commits, tags and pushes. The tag's CI checks the tag matches VERSION, builds the CLI for every OS, and publishes the release as a draft that becomes public only when every file is on it with its checksum. Then two jobs follow it. `brew` clones parham-alvani/homebrew-tap with the `TAP_DEPLOY_KEY` secret (a deploy key with write access on the tap, `ssh-keys/github/daftar-release-tap_ed25519` in the keys repository), moves the `daftar-cli` formula with the same steps as the tap's `bump` workflow, and pushes, which runs the tap's CI; the tap's daily bump is the fallback. `aur` runs `just aur-update` as a user that is not root (makepkg refuses root), then `just aur-push` with the `AUR_SSH_KEY` secret (`ssh-keys/aur/aur_ci_ed25519` in the keys repository), which pushes `daftar-bin` and `daftar-cli-bin` to the AUR and commits the new `PKGBUILD`s to main. When a job fails, run it again from the Actions page, or `just aur` by hand with your own AUR key. The AUR's search API may show the old version for a while after.
